# vpnlock на Linux: устройство и стенд

## Устройство

- Служба — systemd (`/etc/systemd/system/vpnlock.service`, `Type=notify`: `READY=1` через `Deps.Ready` после первых правил, `Before=network-pre.target`). Порядок запуска — только `After=local-fs.target`: `After=systemd-resolved.service` на Ubuntu 22.04 даёт цикл (resolved → networkd → network-pre → служба), и systemd молча выбрасывает запуск. При загрузке resolved и D-Bus поднимаются позже службы, домены повторяются на тике `CheckEvery`. Программа и данные — `/opt/vpnlock`, журнал — `/var/log/vpnlock`, сокет — `/run/vpnlock.sock`, права — группа sudo, wheel или admin (`SO_PEERCRED`). Общее с macOS — `*_unix.go`, `cmd/vpnlock/main_unix.go`.
- Исполнитель (`enforce/nft_linux.go`, `jail_linux.go`) устроен как WFP, а не как pf: закрыто приложение, а не только адреса. Таблица `inet vpnlock` заменяется целиком одной транзакцией `nft -f`, чужие таблицы не трогаются.
  - `guard` — адреса сервисов всем программам, везде, кроме проверенных туннелей (и серверов VPN на физическом интерфейсе). Адреса — `drop`: `exitcheck.Reach` считает отказ достижимостью.
  - `app` — процессам с меткой `meta cgroup`: петля, проверенные туннели, DNS в локальной сети (из `/etc/resolv.conf`, без него нет имён и при VPN), остальное — отказ.
  - `output` до метки пропускает порты сокетов ядра (`procs.KernelUDPPorts`: UDP-сокет без процесса). WireGuard в ядре шифрует пакет на месте, и внешний пакет сохраняет сокет приложения с меткой группы: без этого правила `app` отказывал бы ему на физическом интерфейсе, и у защищённого приложения не было бы сети и через проверенный туннель. Найдено живой проверкой, клиенты в пользовательском пространстве этого не показывают.
  - `state/closed.nft` — те же правила с закрытыми путями. Их грузит `ExecStartPre`: защита с самого старта, до сети.
- Группа процессов — cgroup v1 `net_cls`, а не `socket cgroupv2`: метку не сбрасывает перенос процесса в другой scope (GNOME и snap так делают с каждым приложением), не нужен перезапуск службы или `Slice=`, а при переносе процесса ядро ставит её и на уже открытые сокеты. Минус: у ядра может не быть `net_cls` (openSUSE Tumbleweed), тогда установка останавливается (`enforce.Preflight`). Запасного пути нет сознательно.
- Попадание в группу:
  - fanotify `FAN_OPEN_EXEC_PERM` на файлах и папках приложений — процесс переносится до первой инструкции, потом `FAN_ALLOW`. Запрета нет никогда, при падении службы ядро пропускает всё само. Метки только на файлах приложений; на программы самой службы (`selfTools`: nft, ip, resolvectl, systemctl, loginctl, notify-send) их ставить нельзя: Go запускает через vfork и держит планировщик, запуск упирается в метку, ответить на которую должен этот же процесс, и служба встаёт, а за ней все запуски файла. Воспроизводится на `GOMAXPROCS=1`. Новая программа службы — в `selfTools`. Такие файлы закрывает просмотр. Страховка — `WatchdogSec=60`: цикл сторожа шлёт `WATCHDOG=1` (`Deps.Alive`), встал — systemd перезапускает, и ядро отпускает ждущие запуски.
  - Файлы службы systemd считаются лишь для процессов в её cgroup: `/usr/bin/python3` у службы — не повод закрывать всю систему. Пути из `ExecStart` приводятся к настоящим (`ServiceExecs`): событие приносит настоящий путь.
  - Раз в 10 с метки ставятся заново: обновление меняет inode.
  - Раз в 2 с просмотр `/proc` переносит то, что запуск не поймал: `python3 bot.py` (относительный путь — от cwd процесса), запуск при лежащей службе, уже работающие процессы. Ядро без перехвата — только просмотр.
- Что защищается — `apps.Read`: папка установки или файл (`apps.CommandTarget`), служба — `systemd:<имя>.service`. Всё защищено сразу (`Instant`, `Command`): адреса приложений не учатся, ответы DNS не слушаются (`Answers: nil`), каталог — по имени команды.
  - Команда `/snap/bin/<имя>` — ссылка на сам snap, поэтому снимать её нельзя: защищается `/snap/<имя>` со всеми ревизиями. Обёртка `exec /snap/bin/x` (`/usr/bin/firefox` на Ubuntu) ведёт туда же: значок запускает snap мимо обёртки.
  - `<папка>/bin/<файл>` защищает папку продукта (`binRoot`): значок VS Code запускает `/usr/share/code/code`, а в PATH лежит скрипт `/usr/share/code/bin/code`.
  - Запускатели и интерпретаторы (`apps.Launcher`) отвергаются, их ярлыки не попадают в список. Первое слово `Exec=` у Flatpak и `sh -c` — не приложение.
  - Цель пишется при `add`, исходная ссылка не хранится: `vpnlock check` сверяет команду с целью (`apps.Moved`).
- Сеть: туннели — по sysfs (`tun_flags`, тип 65534/512, не `brport`), маршрут — UDP connect к 192.0.2.1, физический — `/proc/net/route`, привязка — `SO_BINDTOIFINDEX`. Системный прокси не виден: нужен режим TUN.
- DNS — systemd-resolved (`sysdns/sysdns_linux.go`): пустой интерфейс `vpnlock0` (адрес нужен, иначе resolved его не спрашивает), `resolvectl dns vpnlock0 127.0.0.1:53535` и `domain ~домен`. На интерфейс — не больше 256 доменов, на 257-м resolved отказывает всей команде, поэтому большой список раскладывается по `vpnlock1…`. Отказ повторяется на тике `CheckEvery` (`engine.dnsFailed`). Нет resolved — ничего не меняется.
- Приложения — файлы `.desktop` и службы (`apps/desktop.go`, `apps/apps_linux.go`). В `vpnlock add <имя>` совпавшие имена службы и команды — одна программа (`apps.SameProgram`) защищается как программа: так закрыт и запуск руками, а `<имя>.service` — только служба. Разные программы — просит уточнить.
- Каталог обновляет таймер `vpnlock-catalog.timer` с `User=` того, кто ставил.
- Значок (`internal/tray/icon_linux.go`) — StatusNotifierItem по D-Bus, библиотека вкомпилирована. Запускает `/etc/xdg/autostart/vpnlock-tray.desktop` (пишет `Installer`), сразу после установки — `setup/linux/tray.sh` через `setsid`: root к сеансу человека доступа не имеет. Показан значок — открыто соединение с шиной; один экземпляр — flock файла в `XDG_RUNTIME_DIR`.
  - **`Menu` обязателен, хотя меню нет.** Расширение GNOME считает значок готовым только при непустом `Menu` (`appIndicator.js`, `_checkIfReady`, версии 42, 46, 58): без него значка нет, и никакой ошибки. Поэтому выставлено пустое `com.canonical.dbusmenu`: `PopupMenu.open` пустое меню не открывает, щелчок ничего не делает. `ItemIsMenu=false`, `Activate` пустой.
  - На GNOME 42 щелчок средней кнопкой пишет в журнал Shell `TypeError: menu is undefined` (`indicatorStatusIcon.js:252`): код расширения закрывает меню, которого нет. Так с любым значком, на экране не видно.
  - Адрес шины читается сам: `dbus.ConnectSessionBus` без адреса запускает `dbus-launch`.
  - Шина пропала или не подключается — конец сеанса, процесс выходит (`tray.ErrNoSession`). Значок из `setsid` переживает выход из системы и иначе показал бы второй значок при следующем входе.
  - UUID расширения берётся по папке на диске, а не по названию системы: Ubuntu 22.04/24.04 и Debian 12 кладут `ubuntu-appindicators@ubuntu.com`, Fedora и openSUSE — `appindicatorsupport@rgcjonas.gmail.com`.
  - `gnome-extensions enable` только дописывает UUID в настройку `enabled-extensions` и отвечает 0, даже если такого расширения нет. Расширение, которое Shell уже знает, он поднимает примерно за секунду и значок встаёт сам; только что поставленное Shell увидит при следующем входе. `tray.sh` ждёт хост 3 с и по этому выбирает, что сказать. Нет команды или она отказала — скрипт пишет ту же настройку через `gsettings`.

## Сборка и проверка

На маке Linux-код только собирается: `GOOS=linux GOARCH=arm64` и `amd64`. Живьём — виртуалка с настоящим ядром: в Docker Desktop нет fanotify с проверкой прав и `nft_socket`.

Значок без виртуалки проверяется в контейнере: тестовые бинарники `GOOS=linux tools/go test -c ./internal/tray` с настоящим `dbus-daemon` (тесты шины), настоящий GNOME Shell — `gnome-shell --x11 --replace` под Xvfb в ubuntu:24.04 и 22.04, снимок экрана — `import -window root`. Служба в контейнере — заглушка, отвечающая строкой JSON на `/run/vpnlock.sock`. Перед запуском Shell удалить `/run/systemd/seats`: иначе он идёт к logind, которого в контейнере нет, и падает.

Если сервер VPN для проверки стоит в netns на той же машине, его выход наружу идёт через цепочку `forward` службы, и защищённые адреса там режутся. Это свойство стенда: проверять такие адреса надо на стороне сервера VPN (адрес на `lo` внутри netns). Снэпы запускаются только в сеансе пользователя: `systemd-run --machine=ivan@ --user --wait --pipe`, не `sudo -u`.
