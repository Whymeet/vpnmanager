# CLAUDE.md

vpnmanager — внутренний проект: Claude (Desktop, Cowork, Code, сайты) выходит в
сеть только через VPN на нашем VPS. Основа — форк appguard
(https://github.com/XoDefender/appguard, коммит bdcf89c, remote `upstream`;
лицензии у исходника нет). Обзор и установка — `README.md`.

- Своё поверх appguard: `configs/claude-vpn.conf` (Claude + `rule mine`, без
  выходов, тест `TestClaudeVPNConfigParses`), окно «Мои VPN» и одна команда
  установки (ниже), `wsl/` — kill switch для Claude Code в WSL (nftables +
  проверка выхода, bash; фильтры WFP процессы WSL не видят).
- Окно «Мои VPN» — `internal/exitsui/exits.ps1` (WinForms, UTF-8 с BOM,
  встроено в бинарник), установка пишет его в `Layout.ExitsUI`
  (`Program Files\appguard\exits.ps1`: пишет только администратор, окно
  работает с его правами). Без прав окно перезапускает себя через UAC. Всё
  делает `appguard.exe`: `status --json`, `remember`, `forget`, `rule mine`.
  Открывают: `install.ps1` (в окне администратора после `install` и `apply`
  конфига — UAC один раз), пункт «Мои VPN…» щита (`tray.OpenVPN`, задаёт
  `cli/vpn_windows.go`) и `appguard vpn`.
- macOS: конфиг `configs/claude-vpn-macos.conf` (`app Claude`, `app claude`),
  `setup/macos/install.sh` шагом 5 применяет его и открывает `appguard vpn`.
  Окно — диалоги osascript (`cli/vpn_darwin.go`, AppleScript, тексты —
  аргументами), логика общая и с тестами на Linux (`cli/vpn_dialog.go`, шов
  `vpnUI`/`vpnOps`). Пункт щита — `vpn:` в скрипте `tray/icon_darwin.go`
  (показан, если вторым аргументом `vpn`), пишет `vpn` в stdout → `tray.OpenVPN`
  запускает `appguard vpn` отдельным процессом. Права: группа admin, без sudo.
- От автора не тянется ничего само: `catalog sync` без вышестоящей ветки в сеть
  не ходит (`cli/sync.go`, тест `TestNoUpstreamBranchSyncsNothing`). Его правки —
  вручную: `git fetch upstream && git merge upstream/main`.
- Внутреннее имя программы пока appguard (модуль, служба, пути) — переименование
  сломает установленные копии и прежний переход с vpnlock.
- До 0.23.0 инструмент назывался vpnlock. Установка appguard находит прежнюю
  (`paths.LegacySystem`), забирает её настройки и снимает её её же бинарником
  `uninstall --yes` (`install/legacy.go`); переход для людей — «Был vpnlock» в
  `setup/README.md`.
- Установку для ученика описывает `setup/README.md`, его читает агент ученика.
  Меняешь установку — правь и его.

## Сборка и тесты

- Go ставит `setup/macos/prepare.sh` в `.toolchain/` клона (в git не попадает),
  он же собирает `bin/appguard`.
- Файлы запуска по системам: `install-windows.cmd` (только Windows, CRLF) и
  `install-mac.command` (только macOS, проверяет `uname`); тест
  `TestInstallersAreSplit` следит, что каждый берёт свой установщик и конфиг.
  Общий `install.cmd` оставлен для совместимости (Linux, тесты, старые инструкции).
- Установка — одна команда человека: `install.cmd` в корне — один файл на обе
  системы (первая строка `:; exec …` — для sh пустая команда и переход в
  `setup/macos/install.sh`, для cmd.exe — метка; дальше cmd.exe запускает
  `install.ps1` с `-ExecutionPolicy Bypass` и при двойном щелчке ждёт клавишу).
  Переводы строк в нём — только LF. `setup/macos/install.sh` без sudo (шаги
  `[1/5]`: подготовка `prepare.sh --install` от его имени, затем `sudo bin/appguard
  install` и статус; без терминала — отказ, через sudo — возвращается к
  `SUDO_USER`). На Windows `install.ps1` из обычного окна: подготовка
  `-ForInstall`, установка в окне UAC (`-Elevated`), её вывод — через файл
  `-Log`. `prepare` без ключа — для агента, с `--update`/`-ForUpdate` — для
  `appguard update`.
- Разработка — через `tools/go`: тот же тулчейн и то же окружение
  (`tools/go test ./...`, `tools/go vet ./...`).
- Зависимости лежат в `vendor/`, чтобы сборка у ученика не ходила в сеть. После
  `tools/go get …` — `tools/go mod tidy && tools/go mod vendor`.
- CGO выключен: у ученика может не быть Xcode.
- Живые проверки без sudo — тесты с тегом `live`: наблюдатель сети, проверка
  выхода через туннель, служба целиком во временном каталоге
  (`tools/go test -tags live -v ./internal/...`). VPN агент сам не переключает:
  через него идёт и сессия Claude.
- Windows-код пишется на маке вслепую: проверка — `GOOS=windows GOARCH=amd64`
  (и `arm64`) `tools/go build ./...` и `tools/go vet ./...`, живьём — на стенде
  (`_docs/windows-stand.md`, Windows 11 ARM в Parallels, сеть мостом). Тесты,
  которым нужны адаптеры macOS, лежат в `*_darwin_test.go`, живые — с тегом
  `live && darwin`: vet под Windows проверяет и тесты.

## Устройство

- Один исполняемый файл: `appguard daemon` — служба (root, launchd), всё остальное —
  клиент (`internal/cli`). Команды и их аргументы — по-английски (`status`, `add`, `rule mine`…), меню и сообщения — по-русски.
- Клиент ↔ служба — unix-сокет `/var/run/appguard.sock` (`internal/ipc`): строка
  JSON туда, строка обратно (журнал — поток строк). Подключиться может любой
  пользователь; менять настройки — root или группа admin, uid служба узнаёт у ядра
  (`LOCAL_PEERCRED`). Исключение — уведомления (`CmdNotify`): их выключает и
  значок у часов, а он работает без прав.
- `internal/core` — ядро решений без обращений к ОС: пути через туннели, сведение
  двух источников проверки выхода (`Judge`), события журнала.
- `internal/netwatch` — наблюдатель: routing-сокет ядра + снимок туннелей и
  маршрута по умолчанию; системный прокси — опросом `scutil --proxy` раз в 2 с,
  кто слушает порт — `lsof` (помнится 30 с). `internal/exitcheck` — проверка
  выхода: Cloudflare trace по адресу 1.1.1.1 и второй источник из запасного
  списка, запросы привязаны к интерфейсу туннеля (`IP_BOUND_IF`, на Windows
  `IP_UNICAST_IF`), DNS тоже через туннель. Цикл наблюдателя общий
  (`netwatch/watch.go`); на Windows события — уведомления IP Helper, адаптеры —
  `GetAdaptersAddresses`: туннель — тип PROP_VIRTUAL (Wintun, wireguard-nt), PPP
  или драйвер TAP-Windows; маршрут по умолчанию — лучший маршрут до 192.0.2.1
  (ловит и пару 0/1 + 128/1); физический — адаптер со шлюзом и наименьшей
  метрикой.
- Системный прокси — ещё один путь рядом с туннелями (`core.Tunnel.Proxy`, имя
  «прокси адрес:порт»): выход и «Россия напрямую» проверяются через сам прокси
  (CONNECT или SOCKS5, имена разрешает прокси). Пока выход не проверен, порт
  прокси закрыт в pf правилом `… port N user != 0` — для всех программ, кроме
  root: pf не различает программы, а служба проверяет выход через тот же порт.
  Обучение идёт только через туннель: через прокси соединения приложения ведут
  на петлю.
- `internal/journal` — журнал по файлу на день в каталоге службы, 7 дней.
- Ежедневное обновление каталога: установка ставит тому, кто вызвал sudo,
  LaunchAgent `com.appguard.catalog` (`~/Library/LaunchAgents`, раз в сутки и при
  входе) — `appguard catalog sync <клон>`: `git fetch` + `merge --ff-only @{u}` и
  `ipc.CmdSync` (удалось или причина неудачи). Итог принимается от
  администратора или владельца клона, который записала установка
  (`AppDir/clone`); каталог и версию служба читает из этого клона сама, по
  ссылкам за его пределы не ходит (`os.Root`), не больше 1 МБ, причина от
  клиента — одной строкой без управляющих символов. Служба помнит,
  когда каталог сверялся (`catalogChecked`), и напоминает через 7 дней. Задача
  стоит и у автора — перематывает вперёд его рабочий клон, если тот чист и
  отстал. Снимает её удаление (`catalog-agent.json` в каталоге установки).
- «Обновить» (`appguard update [клон]`) запускает человек, как установку:
  `sudo` на macOS, PowerShell от имени администратора на Windows. Клон — из
  аргумента, текущей папки или `AppDir/clone` (его пишет установка). Сборка —
  подготовкой с `--update`/`-ForUpdate` от имени человека (на macOS root
  сбрасывает права до `SUDO_USER`: сборка под root испортила бы кэш в
  `.toolchain`), затем `<клон>/bin/appguard install`. Через службу обновление не
  идёт сознательно: иначе любой процесс администратора без пароля заставил бы
  службу root запустить свой файл.
- «Проверка» (`appguard check`, `ipc.CmdCheck`): служба — правила (`Verify`),
  выход, «Россия напрямую», каждый защищённый сервис мимо VPN (до трёх адресов,
  `exitcheck.Reach` через физический интерфейс, 2 с; серверы VPN через CDN не
  пробуются); клиент — «безопасный DNS» браузеров из профиля человека
  (`internal/browsers`: Chrome/Edge/Brave — `Local State`, режим `secure`;
  Firefox — `network.trr.mode` 2/3 или `doh-rollout.mode`). На шве `Reach`
  отвечает как pf с текущими правилами.
- `internal/notify` — уведомление об открытии (адрес и страна выхода) и
  закрытии (причина) сервисов вошедшему пользователю (владелец `/dev/console`):
  `launchctl asuser <uid> sudo -u #<uid> osascript`, текст — аргументом
  скрипта. Одно на событие (`engine.notification`): тот же текст подряд не
  повторяется, смена выхода при открытых сервисах — новое событие. О закрытии —
  только если оно длится дольше `Deps.NotifyAfter` (15 с; дождавшееся отдаёт тик
  `notifyDue`): переподключение VPN проходит молча, и открытие после него тем же
  выходом тоже. Выключаются настройкой `notifyOff` (`appguard notifications off`
  или меню значка — `CmdNotify` принимается от любого пользователя), журнал
  пишется всегда.
- `internal/tray` — значок службы рядом с часами: есть значок — служба отвечает;
  картинка — защита (щит с замком — в сети, перечёркнутый — без сети); по щелчку
  узкое меню — заголовок, строка под ним (выход или причина), «Уведомления»
  (переключатель на macOS, отметка на Windows и Linux). `appguard tray` — служебная
  команда, как `notify-agent`: цикл (`tray.Loop`) раз в 2 с спрашивает
  `CmdProtection` (`ipc.Protection` — части: адрес, страна, причина), новый ответ —
  `Icon.Update`; пункт меню — `CmdNotify` и `Update` даже с тем же видом. Три неудачи
  подряд скрывают значок, после удаления appguard значок выходит сам, занятое место
  новый экземпляр ждёт до 5 с (обновление снимает старый). Перечёркнутый щит для
  Windows и Linux строится из `shield.png` в коде. Показ — шов `Icon`: на macOS
  дочерний `osascript` (`app.run`; меню 220 pt из своих видов с `NSSwitch`; вид —
  строки JSON из ASCII в stdin, переключатель — `toggle` в stdout, конец stdin —
  выход; LaunchAgent `com.appguard.tray` без
  `AbandonProcessGroup`: launchd снимает группу процессов; путь — из `Agent.Home`,
  формат `catalog-agent.json` не менялся; новый значок macOS ставит левее всех,
  поэтому при первом запуске ему задаётся `NSStatusItem Preferred Position` 0 — у
  часов), на Windows `Shell_NotifyIconW` на закреплённом потоке (задача
  `appguard-tray`, установка делает `/End` перед `/Run`, мьютекс `Local\appguard-tray`,
  `TaskbarCreated`, окно обычное, не `HWND_MESSAGE`, меню — `TrackPopupMenu`), на
  Linux StatusNotifierItem с dbusmenu (`_docs/linux.md`).
- Зонд «Россия напрямую» (`exitcheck.Probe`): Яндекс (ipv4-internet.yandex.net,
  запасной yandex.ru/internet) спрашивается через туннель и через физический
  интерфейс; одинаковый ответ — клиент VPN шлёт российское мимо туннеля. Зонд
  только сообщает: прямые соединения к узлам сервисов в России и так закрывает pf.
- `internal/enforce` — исполнитель на pf: якорь `com.apple/100.appguard` (его уже
  вызывает `anchor "com.apple/*"` из /etc/pf.conf). Таблицы адресов защищённых
  сервисов закрыты везде, кроме проверенных туннелей. **Основной набор pf не
  перезагружать**: пропадут якоря, которые система вставляет на лету (общий
  доступ к интернету, NAT виртуалок Parallels). Исключение одно: набор фильтров
  пуст (его сбросили) — тогда фильтры грузятся из /etc/pf.conf (`pfctl -Rf`, NAT
  не трогается).
- Устойчивость: сторож раз в секунду сверяет правила (`Enforcer.Verify` —
  только чтение: pf включён, точка com.apple на месте, число правил якоря и
  адресов в таблицах) и восстанавливает их. Остановка службы закрывает все пути
  (таблицы остаются); после удаления движок правил не ставит. Метка
  `state/running` отличает перезапуск после обрыва. Серверы VPN — установленные
  соединения мимо туннеля самого клиента VPN, пока выход проверен и «Россия
  напрямую» не замечена (`vpnClientServers` в настройках; прежний `vpnServers`
  не читается — туда попадали соединения любых программ). Клиент VPN — процесс,
  который держит utun маршрута по умолчанию: у него открыт управляющий сокет
  `utun_control` с unit на единицу больше номера utun (`procs.TunnelOwners`) —
  только сокет ядра, у lsof тип `systm`: то же имя бывает и у unix-сокета,
  который заведёт любая программа. Для проверенного пути через системный
  прокси клиент — процесс, который слушает порт прокси (его адрес или «все
  адреса» с тем же портом, `procs.ProxyOwners`): с физического адреса там
  ходят все.
  Совпавший с защищённым адресом (VPN через CDN) разрешён на физическом
  интерфейсе. Клиенты на WireGuard (AmneziaVPN) шлют через неподключённый UDP —
  их сервер в lsof не виден. `sudo appguard uninstall` (`Installer.Uninstall`)
  снимает plist, останавливает службу, затем pf и резолверы (`Installer.Clear`
  — иначе сторож вернул бы правила, а токен pf лежит в каталоге службы) и
  только потом файлы; служба не остановилась — правила и файлы остаются.
- `internal/resolver` — DNS-сервер службы на 127.0.0.1:53535 (порт не 53: там
  часто сидит DNS VPN-клиента). Ответ программе — шифрованный DNS (DoH Cloudflare,
  затем Google, по IP); российский DNS (Яндекс) спрашивается через физический
  интерфейс с ECS /0, его адреса только в таблицы. Ответ уходит после того, как
  адреса легли в pf; не легли — SERVFAIL. `internal/sysdns` — файлы
  `/etc/resolver/<домен>` с пометкой `# appguard`, чужие не трогаются.
- Приложения: `internal/apps` — пакеты .app в папках «Программы» (Info.plist
  через howett.net/plist); `internal/procs` — процессы приложения (`ps`) и их
  соединения (`lsof`), включая вспомогательные и обновлятор (ShipIt/Sparkle в
  `Library/Caches`); `internal/learn` — какие удалённые адреса годятся в
  обучение. Служебные адреса (DoH, проверка выхода, российский DNS) не учатся
  никогда — их список сверяет тест `learn` с `exitcheck` и `resolver`.
  Обучено — после `LearnFor` работы при проверенном выходе и хотя бы одного адреса.
- Консольные программы на macOS (`appguard add claude` или путь): `apps.Read` не
  для .app — `readCommand`; что защищается — `apps.CommandTarget` (папка
  установки: `versions/` у Claude Code, формула в Cellar без папки версии, пакет
  в `node_modules`; в общих папках — сам файл), идентификатор `cmd:<цель>`.
  Процессы — по пути от ядра (`kern.procargs2`, `procs.MatchCommand`): `ps -o
  comm` показывает, как программу вызвали (`claude`); у скрипта — путь в
  аргументах интерпретатора. Учится только до «защищено», потом — лишь новые
  имена своих зарегистрированных доменов (`engine.ownSites`): иначе сайты,
  которые она открывает по просьбе человека, закрылись бы вне VPN для всех. В
  каталоге — `macos.command`, выгрузка пишет имя команды, а не путь. В CLI
  `Claude` — приложение, `claude` — команда: регистр сверяется по папке.
-  Домены приложения: `internal/dnswatch` слушает входящие ответы DNS (BPF,
  фильтр в ядре — только UDP с порта 53) на туннеле маршрута по умолчанию, пока
  его выход проверен и есть приложения; имя из вопроса → адреса ответа (вместе с
  CNAME), кэш — 2 минуты, до 16 имён на адрес. Имя — домен приложения
  (`Protected.Apps`), если его ответ пришёл перед новым соединением приложения с
  этим адресом (проход сканера + 15 с): на общем адресе CDN иначе приписались бы
  сайты из браузера. Такие домены защищаются как домены каталога и уходят в
  выгрузку. Не учатся служебные (запасные источники проверки, Яндекс, DoH —
  `learn.Domain`, список сверяет тест с `exitcheck`) и локальные имена; не
  больше 200 на приложение. Только туннель: ответы мимо него может подделать
  локальная сеть. Зашифрованный DNS приложения (DoH) так не услышать. На Windows
  пакеты без драйвера не послушать — имена берутся из кэша службы DNS-клиента
  (`dnswatch/cache_windows.go`: `DnsGetCacheDataTable` и `DnsQuery` без похода в
  сеть, раз в 10 с; отдаются только пары «имя — адрес», новые с прошлого опроса,
  первый опрос молчит); через какой интерфейс пришёл ответ, кэш не помнит.
- Пропуск TCP в pf — с `flags any`: адрес часто попадает в таблицу посреди уже
  открытого соединения, и без этого pf рвал бы его.
- Ручная защита — без приложения: `protect`/`unprotect` по домену или адресу,
  `appguard import <файл>` — сразу всё из файла (выгрузка `catalog export` или
  список доменов, адресов и ссылок, `catalog.ParseList`; CLI шлёт пачками по
  500: запрос к службе не больше 64 КБ). Домены — `Protected.Manual`, адреса —
  `Settings.Addrs` (`engine.manual`); что закрывать нельзя, отбрасывается
  (`learn.Acceptable`, `learn.Domain`). Статус показывает строку «Вручную».
- Готовый конфиг — `configs/macos.conf`, `linux.conf`, `windows.conf` в клоне;
  применяет `appguard apply [файл]` (`cli/apply.go`): без файла — конфиг своей
  системы (`runtime.GOOS`) из клона (`findClone`, как у `update`). Строки — те же
  команды CLI (`app` → add, `exit` → remember, `rule`, `protect`, `import`,
  `notifications`); файл проверяется целиком до изменений, первая неудача
  останавливает. Программу, которой нет, пропускает (`resolveApp` → `missing`),
  уже защищённую считает сделанной; пути — от папки конфига, `~` и (Windows)
  `%ПЕРЕМЕННАЯ%` раскрываются. Под sudo на macOS и Linux — отказ (PATH и домашняя
  папка были бы root), на Windows — только от администратора. В общих конфигах
  нет `exit` и `rule`: выходы у каждого свои, личный конфиг автора — вне
  репозитория (тест `TestRepoConfigsParse`).
- Мои выходы: `remember` без адреса — текущий проверенный выход, с адресом —
  введённый вручную (`Exit.Unverified`; страну ставит `confirmExit`, когда
  проверка выхода через него прошла). Сам он ничего не открывает:
  `Policy.allows` смотрит только на проверенный выход, российский проверку не
  проходит. `forget <выход>` — по имени (без учёта регистра) или адресу.
  `forget <приложение> <адрес|домен>...` — `engine.forget`: убирает из адресов и
  доменов приложения и пишет в `App.Forgotten`; обучение (адреса и имена, домен
  — с поддоменами) и каталог его больше не возвращают. Что держит приложение —
  `status <приложение>` (`ipc.CmdApp`). В CLI приложение ищет `findApp`:
  точное имя прежде регистра (`Claude` и `claude` — разные).
-  Каталог: `catalog/catalog.json` в клоне (`internal/catalog`, формат с номером
  версии; новее поддерживаемого — не применяется). Установка кладёт его службе;
  `appguard catalog load` — то же без переустановки. Приложение из каталога
  защищено сразу, его домены принадлежат ему (`Protected.Apps`), ручные —
  `Manual`. `appguard catalog export` у автора сливает выученное в файл клона:
  свои домены сервиса — до зарегистрированных (свои — уже свёрнутые в записи
  каталога, из идентификатора пакета `com.openai.chat` → `openai.com` и с именем
  приложения), сторонние (аналитика, отчёты об ошибках) — точным именем; имена
  внутри общих хостингов (частная часть списка публичных суффиксов) отброшены
  как личные, адреса выходов и серверов VPN убирает служба. Что уходит ученикам,
  решает автор — агент выгрузку в коммит сам не делает.
- `internal/tui` — меню стрелками (termios, без зависимостей). Ввод команды —
  один `bufio.Reader` на всё (`cli.Run`): иначе ответ «да» после выбора терялся.
- Живой тест pf требует root: собрать `tools/go test -c -tags live -o
  /tmp/appguard-enforce.test ./internal/enforce`, запускает автор под sudo
  (сборка под sudo испортит кэш в `.toolchain`). То же — BPF:
  `./internal/dnswatch` → `/tmp/appguard-dnswatch.test`.
- Пути установки — `internal/paths`, все вне репозитория.
- Шов тестов — служба целиком с подменёнными адаптерами ОС
  (`internal/service/servicetest`). Сценарии из спеки пишутся на нём.
- **Windows.** `appguard daemon` — служба Windows (`svc.Run`, LocalSystem,
  автозапуск, перезапуск по правилам восстановления; остановку не от appguard
  служба завершает с ошибкой, чтобы они сработали, — обновление и удаление
  заранее шлют ей свою команду `paths.PlannedStop`), вывод — в
  `ProgramData\appguard\logs\daemon.log`. Программа — `Program Files\appguard`
  (папка `bin` дописана в системный PATH), данные — `ProgramData\appguard` с
  защищённым ACL (state — только SYSTEM и администраторы). Канал — два
  именованных канала, `\\.\pipe\appguard` (всем) и `…-admin` (SYSTEM и
  администраторы): «менять — только из PowerShell от имени администратора»
  проверяет ядро по ACL, служба лишь смотрит, через какой канал пришёл клиент
  (`ipc.Peer.Admin`). Клиент верит каналу, только если его владелец — SYSTEM или
  администраторы (имя канала может занять кто угодно). Удаляет `appguard
  uninstall` на месте, от имени администратора: служба свой exe снять не может, а
  работающий exe клиента уезжает в `Windows\Temp` до перезагрузки.
- **WFP** (`enforce/wfp_windows.go`, привязки к fwpuclnt.dll —
  `fwpm_windows.go`, без библиотек: у `tailscale/wf` в зависимостях staticcheck,
  он затащил бы в `vendor/` x/tools). Приложение — по exe (`apps.Read` на Windows,
  `Instant`: защищено сразу), правила — `Rules.Apps` и `Rules.OpenAddrs`. Запрет
  приложению на уровнях ALE — постоянный фильтр (переживает перезагрузку и
  падение службы) плюс загрузочный (до старта BFE, best effort, отказ — в
  вывод службы); разрешение «приложение с адреса проверенного туннеля» — в
  динамической сессии: служба умерла — Windows сама его сняла. Петля разрешена.
  Идентификаторы фильтров — хэш смысла (`ruleID`), какие приложения под
  фильтрами — `state/wfp.json`; по ним снимает `appguard uninstall`
  (`Installer.Clear` — после остановки службы, до удаления файлов). Раскладка
  структур WFP сверяется при сборке; живьём — `TestLiveWFP…` на стенде.
-  **Приложения на Windows.** Список — ярлыки «Пуска» (`apps/lnk.go`, разбор
  .lnk без Windows) и Store (`Get-StartApps`, `apps/store.go`). Что защищается —
  `apps.InstallTarget`: папка установки exe, а в общих папках (Windows, Program
  Files, корень и стандартные папки профиля) — только сам exe; Store —
  `package:<семейство>`. Исполнитель раскрывает цель в программы (все exe папки;
  у пакета — SID контейнера и exe его папок в WindowsApps) и следит за папками
  (`ReadDirectoryChangesW`, подстраховка — пересборка раз в 30 с): новая версия
  встаёт под фильтры сама. Имя для людей — из ярлыка (`Request.Name`), что
  защищается — по пути. Защищено приложение сразу, а адреса и домены сервиса
  (для браузера) учатся фоном, пока путь проверен: процессы — снимок процессов и
  полные пути exe, к приложению их относит `procs.Target` (папки пакета —
  `apps.PackageDirs`), соединения — `GetExtendedTcpTable` (только TCP: таблица
  UDP удалённых адресов не знает). Петля и все разрешения — в динамической
  сессии; закрытый прокси — запрет защищённым программам на адрес и порт прокси
  (вес выше петли), открытый — разрешение. Системный прокси — WinINET того, кто
  за экраном (`WTSQueryUserToken` → `HKU\<SID>`), раз в 2 с; разбор
  `ProxyServer` — `netwatch/proxy.go`.
- **Адреса сервисов и DNS на Windows.** Адреса из таблиц — постоянный запрет
  всем программам (по фильтру на адрес на уровне исходящих; ставится разница с
  прошлым разом, все — после открытия сессии или расхождения у сторожа); всё с
  адреса проверенного туннеля — разрешено; сервер VPN на таком адресе (CDN) —
  разрешён всем, кроме защищённых приложений (вес запрета приложению выше).
  Серверы VPN на Windows — установленные соединения TCP с адреса физического
  адаптера (`GetExtendedTcpTable`, разбор — `procs/tcptable.go`) процессов с
  повышенными правами или SYSTEM: кто держит адаптер туннеля, без перебора
  дескрипторов ядра не узнать, а открыть его может только администратор. Таблица
  UDP удалённых адресов не знает — сервер на UDP (WireGuard) не виден.
  Резолвер — `127.53.53.53:53`: NRPT порта не знает, а на `127.0.0.1:53` часто
  DNS клиента VPN. Правила NRPT (`sysdns/sysdns_windows.go`) — в реестре
  `…\Dnscache\Parameters\DnsPolicyConfig`, по 50 доменов с ведущей точкой,
  метка `Comment = appguard`; если правила задаёт групповая политика, локальные
  Windows не читает — служба пишет об этом в журнал.
  Клиенты VPN на sing-box (v2RayTun, Hiddify, NekoBox) в режиме туннеля ставят
  свой подуровень WFP веса 0xffff (в своей динамической сессии) с запретом
  всем на порт 53 мимо их туннеля — под него попадает и петля к резолверу.
  Положить разрешение в чужой подуровень нельзя (`FWP_E_WRONG_SESSION`), а
  обычный запрет фильтра в WFP окончательный, порядок подуровней равного веса
  не обещан. Поэтому два слоя: в своём подуровне — жёсткое разрешение «петля,
  порт 53» (`FWPM_FILTER_FLAG_CLEAR_ACTION_RIGHT`, помогает, если наш подуровень
  смотрится первым), и `engine.resolverLoop` (все системы): служба раз в 3 с
  спрашивает свой резолвер по петле запросом без вопроса (FORMERR без похода в
  сеть); два промаха подряд — домены снимаются с системы (`dnsBypass`, имена
  разрешает DNS системы — у такого клиента через туннель), ответил — домены
  возвращаются. Адреса в таблицах остаются закрытыми. `appguard check` — пункт
  «Резолвер». Шов тестов — `Deps.ResolverUp`, `Fakes.ResolverDown`.
- **Уведомления на Windows**: у службы нет сеанса, поэтому она раздаёт их по
  каналу (`ipc.CmdNotifications`, подписчики — `service/hub.go`), а
  показывает агент `appguard notify-agent` в сеансе пользователя. Его запускает
  задача планировщика `appguard-notify` (группа «Пользователи», при входе) из
  `appguardw.exe` — той же программы, собранной с `-H=windowsgui`, чтобы
  при входе не мигало окно. Показ — PowerShell с WinRT-уведомлением, текст —
  переменной окружения. Агент выходит сам, когда appguard удалён. Работающие
  exe при обновлении и удалении уезжают в `Windows\Temp` (`moveAside`).
- **Каталог на Windows**: приложение находится в каталоге по имени exe, которым
  его добавили (`config.App.Exe`, `catalog.ForWindows`), или по семейству
  пакета Store — так у него без обучения есть домены и адреса. Ежедневное
  обновление — задача `appguard-catalog` от имени того, кто ставил appguard,
  **без повышения** (хук git в клоне, куда пишут обычные программы, с
  наивысшими правами получил бы права администратора без UAC; итог служба
  принимает от владельца клона), из `appguardw.exe`; git — из PATH, без окон
  (`CREATE_NO_WINDOW`,
  `GCM_INTERACTIVE=never`). «Безопасный DNS» браузеров — те же настройки в
  `AppData` (`browsers.check` знает обе раскладки).

## Грабли

- **sudo агент не запускает.** Живые проверки — установку, правила файрвола,
  перезагрузку, запись трафика — выполняет автор; агент даёт точную команду.
- Код возврата функции Windows через `proc.Call` — `uint32(r)`: старшая
  половина регистра не определена, на ARM64 HRESULT приходят с расширенным
  знаком (`0xffffffff80320009`) и не совпадают с константами (`enforce.result`).
- Git для Windows кладёт клон с CRLF (`core.autocrlf`): что читается из клона,
  сверяется без `\r` (`install.IsClone`).
- `script` на macOS теряет ввод из трубы — диалог с подтверждением проверяется
  через `expect` (`spawn appguard uninstall`, ответ `send "да\r"`).
- Путь unix-сокета не длиннее 104 байт, а временные каталоги тестов на macOS
  длиннее — в тестах сокет лежит в `/tmp` (`servicetest.Socket`).
- `launchctl bootstrap` сразу после `bootout` иногда отвечает «5: Input/output
  error» — в `install.Launchctl` для этого повтор.
- `.ps1` в `setup/windows/` — UTF-8 **с BOM**: без него Windows PowerShell 5.1
  читает файл в кодировке системы и ломает русские строки. `$ErrorActionPreference
  = 'Stop'` там не ставить: в 5.1 с ним строка программы в stderr обрывает
  скрипт. Запуск — `powershell -NoProfile -ExecutionPolicy Bypass -File …`:
  по умолчанию сценарии в Windows запрещены.
